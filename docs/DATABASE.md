# Vector Store, Index & Asset Storage Specification (DATABASE.md)

## 1. Storage Architecture Overview
**OmniDoc-Vision** manages three synchronized storage layers:
1. **Qdrant Vector Database (`omnidoc_vision_chunks`):** Stores 1024-dimensional dense `BAAI/bge-m3` embeddings and rich multimodal metadata payloads (`modality`, `bounding_box`, `image_path`, `table_html`).
2. **BM25 Sparse Index (`data/bm25_index/`):** Stores tokenized text, table headers/cells, and technical figure captions for exact identifier and metric matching.
3. **High-Resolution Visual Crop Store (`data/crops/`) & Redis Cache (`redis:7-alpine`):** Stores extracted `.png` crops of figures/tables on disk and caches frequent multimodal query responses in Redis.

---

## 2. Qdrant Collection Schema (`omnidoc_vision_chunks`)

### 2.1 Vector Configuration
- **Collection Name:** `omnidoc_vision_chunks`
- **Vector Size:** `1024` (`BAAI/bge-m3`)
- **Distance Metric:** `Cosine`
- **On-Disk Payload:** `True`

### 2.2 Multimodal Payload Schema (JSON)
Every point stored in Qdrant adheres to the `MultimodalChunk` contract. Bounding boxes are normalized page-relative rectangles in `[0, 1]`; the default origin is `TOPLEFT`.

```json
{
  "chunk_id": "doc_aurora_bench_p04_fig01",
  "doc_id": "doc_aurora_bench",
  "doc_name": "aws_aurora_postgres_benchmark_2026.pdf",
  "page_number": 4,
  "modality": "figure",
  "section_title": "4.2 P99 Latency Under High Connection Concurrency",
  "content": "[FIGURE CAPTION & TECHNICAL SUMMARY] Line chart comparing P99 write latency (ms) on Y-axis against Concurrent Connections (50 to 500) on X-axis for Aurora PostgreSQL vs Standard RDS. At 250 connections, Standard RDS latency spikes from 45ms to 620ms, while Aurora remains at 38ms.",
  "table_html": null,
  "image_path": "data/crops/doc_aurora_bench_p04_fig01.png",
  "bounding_box": {
    "page": 4,
    "x0": 0.19,
    "y0": 0.285,
    "x1": 0.882,
    "y1": 0.71,
    "coord_origin": "TOPLEFT"
  },
  "ingestion_timestamp": "2026-10-30T18:00:00Z"
}
```

### 2.3 Payload Variations by Modality (`modality` field)
| Modality (`ChunkModality`) | `content` Field (Indexed by BGE-M3 & BM25) | `table_html` Field | `image_path` Field |
| :--- | :--- | :--- | :--- |
| `"text"` | Clean reading-order Markdown paragraph with section header prefix. | `null` | `null` |
| `"table"` | Markdown table representation + column header summary for dense/sparse search. | Full lossless HTML `<table>...</table>` structure preserving `colspan`/`rowspan`. | Optional PNG crop of the table region (`data/crops/..._tbl01.png`). |
| `"figure"` | Structured technical summary generated by `visual_captioner.py` (Title, Axes, Series, Key Values). | `null` | Relative path to high-res PNG crop (`data/crops/..._fig01.png`). |

---

## 3. Payload Indexes in Qdrant
To support fast metadata filtering (e.g., filtering only `"table"` or `"figure"` chunks or restricting to a specific `doc_name`), the following Qdrant payload indexes are created at startup:
- `modality` (`Keyword` index)
- `doc_name` (`Keyword` index)
- `page_number` (`Integer` index)

---

## 4. Redis Response & Visual Asset Cache
- **Key Format:** `omnidoc_vision:v1:query:{sha256(normalized_query + modality_filter)}`
- **TTL:** `3600` seconds (1 hour).
- **Cached Value:** Serialized `MultimodalQueryResponse` JSON (including answer, route taken, citations, bounding boxes, and image crop URLs).
